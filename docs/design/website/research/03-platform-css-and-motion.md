- **GSAP licence:** commercial use is free, all plugins included. Two restrictions: no use in no-code visual
  animation builders that compete with Webflow, and Webflow may terminate the licence for non-compliance. This
  makes it proprietary, not OSI open source: an exit and licence risk for C3 and C9.
- **Scroll performance evidence:** Chrome docs (2023-05-05) say scroll events reach JS "asynchronously" and "main
  thread animations are subject to jank". Scroll timelines run "off the main thread". In Chrome's case study (about
  mid-2023, Chrome 116 and later), the CSS version was "completely unaffected by the heavy JavaScript work" while the
  JS version went "janky and sluggish". The figures are only in screenshots, with no number in the text.
  Tokopedia (Chrome case studies, about May 2024): "average CPU usage reduced from 50% to 2% while scrolling" and up
  to 80% fewer lines of code. That is a vendor-reported case study: a lead, not a benchmark. The off-thread benefit
  holds only for composited properties: `transform`, `opacity` (`clip-path` is not composited in Chrome).

### Does "spring in the build" need a spring library?

**No.** The spec gives a fixed duration and curve: 380 ms / 520 ms expo-out. A critically damped or over-damped spring
is visually an expo-out, so a CSS transition with `cubic-bezier(.16,1,.3,1)` matches the artboard exactly. That is the
expo curve the handoff's keyframes already use. If a visible spring (slight overshoot) is wanted, sample the spring at
build time into a `linear()` easing string, which is widely available since 2026-06-11. That needs no runtime JS and
is the same trick Motion mini uses internally.

What only a JS spring adds: it keeps velocity when interrupted. A CSS transition retargets from the current position
but restarts from zero velocity. Here the lens target only changes when the pointer crosses into a new 8x16 cell, so
retargets are discrete steps. A velocity seam there is not visible in practice (judgement; no measurement). If a
spike proves otherwise, Motion mini (3.5 kB gzip, MIT) is the smallest upgrade.

### Boot curtain detail (highest risk)

- An inline synchronous `<head>` script (about 150 bytes) sets `data-boot` on `<html>` when `sessionStorage` has no
  flag and the user does not prefer reduced motion. CSS shows the curtain only under `[data-boot]`, so no JS means no
  curtain (fails open).
- Any key: on `keydown`, call `getAnimations()` and `.finish()` on each, or remove the node. On `animationend` of the
  last layer, remove the node.
- The handoff keyframes animate `clip-path` with `steps(24)` and `steps(14)`. These are paint, not composite, but at
  24 discrete frames over about 0.8 s the cost is negligible.
- **LCP risk (unverified; needs a spike):** Lighthouse starts each run with a fresh session, so the curtain plays in
  every audit. Its layers start at `opacity: 0` and become visible later. Its noise tiles are 560x384 background
  images, and its log text may be large. Any of these can become a later, larger LCP candidate than the hero text,
  pushing LCP towards about 1.8 s. Measure it. Mitigations: keep curtain pieces smaller than the hero text block, or
  build the noise from many small tiles.

## Open questions

1. Boot curtain vs LCP and CLS in Lighthouse (fresh session every run). Spike it first.
2. Fallback for the 3 scrubs in Firefox ESR 153 and Safari < 26: crossfade (recommended, matches the
   reduced-motion spec) or a JS scrubber? This is the designer's call; I recommend the crossfade.
3. Does the lens need visible overshoot? If yes, generate `linear()` at build time; confirm with the designer.
4. Should the eye slip and the scan band pause offscreen? The spec says "in view only" only for the heading echo.
